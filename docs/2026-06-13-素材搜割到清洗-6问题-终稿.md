## 问题 1 · 批量清洗导致磁盘爆满

### 现状与根因(实测)
- **磁盘已爆,不是将来**:`df -h ~` = 228Gi 盘已用 193Gi,**剩 3.0Gi / 99%**;`~/Downloads/af素材` 占 2.9G,根目录直挂 **82 个 mp4**(全是批量清洗垃圾),子目录仅 5 个(正常留档)。
- **主根因**:批量清洗走 `handle_clean()`(`download_server.py:519-557`),逐条 `process()` 下载 → `_upload_item()` 传 node2,**上传成功后没有任何 `os.remove`**。素材真正归宿是 node2,本地这份是纯垃圾却永久留存。
- **次根因(还会重复下载)**:`/clean` 的 POST body 没带 `dir`(`apply_verdicts.py:304`)→ `resolve_outdir(None)` 退回 `DEFAULT_DIR=~/Downloads/af素材` 根目录;而 `/download` 落在 `<选题>/` 子目录。两路径不同 → `process()` 的幂等 skip 永远跨不过 → 同一素材两路径各下一遍。
- **删除安全边界**:图文笔记 `dl_xhs_images` 落 `_01.jpg/_02.jpg` 多张但 `res["file"]` 只返回首张(`:180`),裸删只删一张;`handle_clean` 全程不写 manifest,无法靠它反查。

### 落地方案(改 2 文件,~10 行,无新依赖)
- **第 0 步 救火**:上面的清盘命令。
- **第 1 步 主修**(`download_server.py:542-547`):`_upload_item` 返回 True 后按目录/前缀删本地(覆盖图文多张);失败则保留入 pending。
- **第 2 步 隔离**(`handle_clean` 头部):下载目录从共享 `outdir` 改成 `outdir/.clean_tmp`(点开头 Finder 隐藏)→ 清洗过路件与留档物理隔离,可放心整目录删,且不再污染选题根目录。
- **第 3 步 兜底**(`__main__` 启动块 +3 行):`shutil.rmtree` 清掉上次崩溃残留的 `.clean_tmp`。不上 cron/守护(每跑流水线都重起 server,够了)。
- **第 4 步 配套**(`apply_verdicts.py:304`):`/clean` body 加 `dir`(复用页面顶部目录框),让 `.clean_tmp` 落对选题、目录归类正确。

## 问题 6 · 下载稳定性 + 高可用兜底 + 预检 ⭐(你最关心)

### 现状与根因(全部 Read 代码 + 实跑核实)

**A · "待清洗"永久卡死 = 双侧都缺"必收敛"保证(最高优先,先治)**
- `handle_clean` 是单请求线程内**串行逐条**跑(`:537-556`):单条 yt-dlp 超时 600s、YT-new 900s、上传 900s,多条叠加单批可达数十分钟。
- 已有的兜底:`handle_clean` 对 process 异常会导向 `_fail_item`,末尾还有 pending 补发——所以**单条下载失败本身能收敛**。
- **真正漏网两种**:① 串行阻塞——某条卡满 600/900s 期间,它和后面还没轮到的条目在 node2 全是 `loading`;② 进程被 kill / Mac 休眠 / 前端断 / node2 不可达 → for 循环走不到收尾 → 已建占位但未处理的条目**永远 loading**。
- **node2 侧零运行期兜底**:`clean_start` 建 `loading` 占位(`app.py:315`),运行期唯一能 loading→failed 的路径是 download_server 主动回调;`store.reconcile` 只在**重启**时把 loading→failed。即:download_server 不回调,node2 运行期该条 **loading 永不超时**。一条永 loading → job 永 queued → SSE 永不收手 → cleanup 永不回收 → 页面长期"待清洗"转圈,**无自愈、无人工清除入口**。

**B · 四平台单工具单路径,IP 归因要按平台拆(一手实测)**

| 平台 | 实测 | IP 相关? | 真因 |
|---|---|---|---|

## 问题 4 · 多开 Claude 会话并行(端口互不影响)⭐(你最关心)

### 现状与根因(一手端口实验印证)
- **根因1 三处固定端口 + 一个共享目录**:`download_server:18/594` 固定 8788、`writer_server:10/31` 固定 8799、选片页 `http.server 8765`;`BROLL_RES` 不显式设就同写 `results/`(scored/verdicts/filtered.html/xhs_imgs.json 互相覆盖,**比端口更隐蔽因为不报错**)。
- **根因2(最坑)出页把端口烘焙进静态 HTML**:`apply_verdicts.py:342` 把 JS 里 `127.0.0.1:8788` 用 `DLPORT` 替换后**一次性写盘**。所以"页面连哪个端口"在生成那刻就定死;哪怕第二个 server 起到别的端口,会话 B 的页面仍打到会话 A 的进程(用 A 的 BROLL_RES,xhs_imgs/token 全错位)。
- **纠偏(必须讲清):第二个 server 不是"抢走"老的,而是自己崩**。一手实测:`bind 8788` 第二次 → `errno=48 Address already in use`;`SO_REUSEADDR` 仍失败 → **macOS 下同端口共用不可行,必须各会话各端口**;`bind(0)` → OS 自动分配空闲端口(62785...)→ **动态端口可行**。
- **"清洗被迫终止"的真实因果链**:撞端口 → `preflight.sh:66` 建议"先 kill 占用进程" → 用户去 kill 占 8788 的进程 → 杀掉的恰是会话 A 正在 `handle_clean` 边下边传 node2 的活进程 → 在途条目走不到收尾 → node2 那条**永停 loading**。即 **kill 活进程是唯一的清洗杀手**(单纯下载失败有 pending 兜底,不致命)。
- node2 侧不冲突(job_id = uuid 天然隔离),**别动它**。

### 落地方案(改 6 文件但都局部,纯标准库,不动 node2)
- **D1 端口自适应 + sidecar**(治撞端口崩/被迫 kill):`download_server` 入口从 `DOWNLOAD_PORT` 起**向上探测第一个空闲端口**(try bind 捕 OSError 则 +1,试 ~10 个);成功后 print 机器可读 `DOWNLOAD_PORT=<n>` + 写 sidecar `RES/.dlport` + `atexit` 删之。`writer_server` 同款(8799 顺延 → `RES/.writerport`)。**多会话各起各的、自动错开,再也不用 kill 别人进程。**
- **D2 出页运行期发现端口(最关键)**:删 `apply_verdicts.py:342` 的端口固化;JS 顶部改为同源 `fetch('.dlport',{cache:'no-store'})` 读真实端口拼 `BASE`,EP/PV/pickdir/clean/preview 全用 `BASE`。**彻底解掉"端口烘焙进 HTML→连错进程"**。加固:新增无副作用 `GET /ping` 返回 `basename(RES)`,JS 校验选题一致再用(二期)。
- **D3 选片页 + 收割 JS 也走同源发现**:`SKILL.md:30` 选片页改 `TCPServer(('127.0.0.1',0))` 让 OS 分配端口并打印真实 URL;收割 JS 的 `:8799` 改成从 `.writerport` 读。
- **D4 会话级隔离 + kill 兜底**:① 把"多开必带独立 `BROLL_RES=$PWD/results_<选题>`"从可选纪律**升为硬步骤**;② 收割 JS 的 localStorage 全局键 `dyAll`/`xhsAll` 改带 SID(否则同域两会话互相清空/混入——另一处隐蔽串数据);③ `download_server` 加 `SIGTERM/SIGINT` 处理:收到信号先对未确认 sid 补一轮 `_fail_item`,把"被 kill=孤儿 loading"降级成"被 kill=明确 failed 可重试";④ `preflight.sh:66` 文案从"kill 占用进程"改为"多开为常态、端口自动顺延、勿 kill 他人进程、各用独立 BROLL_RES"。

> **诚实边界**:**浏览器收割阶段不能真并行**(单 Chrome 单动作流是物理约束,Claude-in-Chrome 按账号连一个实例)。**下载/B站YT后台轨可真并行,但收割须串行**——别承诺收割也能并发。

## 问题 3 · 清洗任务"全部终止"

### 现状与根因
- **node2 零 cancel 能力**:`app.py` grep cancel/terminate/stop/abort/kill 零命中;`_jobs` 六态无 cancelled;`_q` 是标准库 Queue,入队条目无法撤出;worker 取到即进 `_process`,无检查点。
- **已 processing 的物理上无法外部强杀**:worker 是 `daemon Thread`(无 stop 原语),`clean_one` 内 VLM httpx 流 / PaddleOCR(C++ GIL) / ffmpeg `subprocess.run`(未暴露 Popen)都不可中断。
- **投递端 download_server 也是不可中断同步循环**,且 node2 即便标取消,只要 handle_clean 还在跑就会把取消条目重新推回 queued。

### 落地方案(协作式取消,两波次)
**波次一(P0·必做·~0.5天·改 3 文件加法)**
- node2 `app.py`:加 `cancelled` 态 + `_recompute_finished_or_cancelled`;`clean_item` 去重 guard 加 `cancelled`(防取消后迟到 upload 回流);新增 `POST /api/jobs/{id}/cancel`(单 job)+ `POST /api/cancel-all`(全部终止,drain `_q`);`_worker` 取队后进 process 前加 cancel 检查点;**`_cleanup_old` 加 loading 超时兜底**(与问题6步骤1同源,单独就能止血卡死)。鉴权照抄 `kb_upload`(job_id 作能力凭证,不走 token)。
- `download_server.py`:加 `_cancel_flags` dict + `/cancel_clean` 端点;`handle_clean` 每轮开头查 flag→break,未投递的走 `_fail_item`。
- `index.html`:加红色"全部终止"按钮(有 loading/queued 时显示)→ 先 POST `:8788/cancel_clean` 停投递,再 POST node2 `/cancel`,刷新;SSE 收尾认 cancelled。

**波次二(P1·可选·+1天)让正在渲染的 ffmpeg 立即停**:`execute.py` 把 `subprocess.run` 改 `Popen+communicate` 暴露句柄 + `kill_job_procs`;`pipeline.py` 加 cancel_check 检查点。**诚实边界**:已进入 VLM httpx 流的条目最坏要等其自然结束(0~300s)——Python 线程模型物理限制,P1 也只能缩短不能消除。

### 待你拍板
要不要"点了立刻停掉正在渲染的 ffmpeg"(要则上 P1;不要则 P0 下 processing 中的条目会跑完当前 clean_one,4.5min 片约 108s,才收手)。

## 问题 5 · 文件名规范(≤70字符、无空格/emoji/乱码)

### 现状与根因(实测复核)
- `sanitize()` 只把 `/\:*?"<>|` 等换 `_`,**保留空格、不去 emoji、不去 `#话题`**。实测 `🔥AI工具 大盘点 #超实用` → 文件名仍含 `🔥`/空格/`#`;`⚽` 原样进。
- `build_name()` 各段独立截断后直接拼接,**无总长上限**。实测最坏 YouTube+小红书 sid = 108 字符 stem + `.mp4` = 112,全中文 ≈324 字节。
- **关键结构事实**:本地落盘 / manifest / 投 node2 四处全部来源于 `build_name()` 一个函数 → **只改 `download_server.py` 的 sanitize + build_name 两个函数,四处自动一致**。

### 落地方案(改 2 函数,~25 行,纯字符串逻辑)
- 重写 `sanitize()`:去 SMP emoji(`\U0001F000-\U0010FFFF`)+ BMP 杂项符号/箭头、空格→`_`、`#` 和路径非法字符→`_`、合并下划线。不再截断(截断上移)。
- 重写 `build_name()`:加 `MAX_FNAME=70` 守卫,固定开销=`平台+_+_+sid+.mp4`,剩余 budget 动态分配(有稿名时稿名≤budget//3、其余给 title;无稿名 title 独占),保证 `len(name+'.mp4')≤70`。格式 `{平台}_{稿名/标题}_{sid}`。
- 回归:对 1000 组随机输入断言 `≤70 且无空格/#`。
- (建议同批)node2 `_safe_name` 把 `root[:180]` 改 UTF-8 字节截断(纯防御,防其他客户端投超长中文名落盘 500)。

### 待你拍板
命名格式:**① 保留 stable_id `{平台}_{稿名/标题}_{sid}`(推荐,只改 2 函数、内容稳定可对账)** vs ② 去 sid 改"平台+序号"`{平台}{序号}_{标题}`(更短但要全链路透传 seq 6 处、跨批不稳定)。
> 注:你原话要"平台+平台序号+口播稿标题"。同事核实"平台序号"是批次局部、跨批/重启会变(不稳定),且要改 6 处;而保留 sid 更稳、改动最小。两者都给了实现,默认按 ① 落地,你定。
